xff v0.9.0

Versioned benchmark fixture layouts

Status and purpose

This document defines reusable, versioned filesystem layouts in the benchmark collector. The v2
registry, prepared-layout lifecycle, report identity, and viewer labels are implemented for local
collection. The remaining rollout is deliberately local: remeasure on the two participating local
machines and use that evidence to decide whether hosted CI should change.

The change addresses three limitations in the current generated fixtures:

  • broad is one flat directory, while deep distributes paths through an artificial depth rule;
  • every worker/count cell rematerializes its own tree, so related measurements do not observe the
    same inode population and filesystem history; and
  • the names broad and deep do not identify which topology generated a report.

Historical reports remain valid descriptions of their original workload. They must not be relabeled
or compared as though they used the new topology.

Decisions

  1. A generated layout has a stable logical name and an explicit revision. Layout revision is part of
    dataset identity and is visible in every viewer surface that identifies a dataset or measurement.
  2. The initial experiment introduces revised broad and deep layouts for local collection only.
  3. One immutable maximum-size tree per layout contains direct traversal anchors for all standard
    file counts. An anchor for a smaller count is contained by the next larger anchor.
  4. A local run prepares and retains both complete layouts for the run. Measurements do not add,
    remove, or move fixture entries.
  5. Collection order is commit, layout, worker count, then file count. The prepared anchors also make
    other iteration orders possible, but the chosen order is part of the collection contract.
  6. Hosted CI keeps its current layout initially. Switching CI is a later decision based on the local
    results, capacity, runtime, and the value of continuity with existing history.
  7. flat is reserved as a possible future extreme workload. It is not collected and does not appear
    as an empty viewer option in this change.
  8. Unused hosted datasets with the obsolete four-worker allocation are retired independently of the
    layout experiment.

Terminology

Term Meaning
Layout A named filesystem-topology family such as broad or deep
Layout revision An immutable definition of that family's topology, anchors, and generation algorithm
Prepared layout One materialized maximum-size tree containing every standard-count anchor
Anchor The directory used as the traversal root for one requested regular-file count
Fixture revision The generator and manifest semantics used to materialize and validate a layout
Dataset recipe The complete compatibility identity for a published series, including its layouts
Legacy layout The current flat broad or depth-distributed deep generated by fixture version 2

The display spelling should combine logical name and revision unambiguously, for example
broad/v2 and deep/v2. The exact punctuation may follow existing UI conventions, but a bare
broad or deep is insufficient wherever reports from more than one revision can appear.

Layout contract

Common properties

Each generated layout revision defines:

  • the ordered supported file counts;
  • the maximum count and anchor-containment rule;
  • directory depth and fanout rules;
  • regular-file placement, naming, and content;
  • placement and counting rules for .gitignore, file symlinks, and directory symlinks;
  • generator/fixture revision and canonical tree-hash algorithm; and
  • any filesystem preparation required before the first measurement.

These values are data in a layout registry, not conditionals inferred from the words broad and
deep. Custom imported fixtures remain independent inputs and retain their existing exact-count and
hash identities.

Every standard anchor contains exactly its advertised number of regular files in its traversal
subtree under the benchmark's normal no-follow policy. The existing convention that .gitignore
counts as a regular file remains unchanged unless a future fixture revision explicitly changes it.
Directories and symlinks do not contribute to the advertised count.

For adjacent counts a < b, the directory used for anchor a is within the traversal subtree of
anchor b. The additional regular files and the smaller anchor directory together bring the larger
subtree to exactly b regular files. Consequently, one maximum anchor supplies every smaller
workload without copying or selecting a prefix at measurement time.

Conceptually, an anchor chain may look like this:

anchor-100000/
  additional entries for 100000
  anchor-50000/
    additional entries for 50000
    anchor-20000/
      ...
      anchor-10/

The anchor directories are observable topology. Their names, nesting, and contribution to path
depth are therefore part of the revision, not an implementation detail. Generation must be
deterministic for a given registered recipe.

Broad revision

The revised broad layout models a shallow, high-fanout tree rather than a single directory holding
all files. Successive anchors sit next to the files and directory groups that fill the difference to
the next count. The layout should use moderate per-directory populations and enough sibling
directories for traversal workers to find useful parallel work.

The layout continues through 100,000 files for the local experiment. That scale is intentionally an
extreme, but a distributed broad tree is more representative than the legacy 100,000-entry flat
directory and can expose worker-scaling behavior hidden by a single-directory bottleneck.

Revision 2 places at most 64 generated files in each leaf group. Remainders occupy the final group
at the same level. This gives the 100,000-file anchor many sibling directories while keeping its
maximum regular-file path depth at 15, including the observable anchor chain. The parameters satisfy:

  • bounded shallow depth across the entire count range;
  • more than one traversable directory at scales where multiple workers are measured;
  • no discontinuous topology change caused only by crossing a standard count boundary; and
  • exact anchor counts without runtime filtering.

Deep revision

The revised deep layout models narrow, bounded-depth traversal. It uses chains whose directories
contain at most 512 generated files, rather than making depth grow once per file or distributing
files by the legacy modulo rule. The registered 100,000-file tree has a maximum regular-file path
depth of 98, including the observable anchor chain.

The registered revision must keep depth meaningful at small and large scales while avoiding a
pathological 100,000-component chain. It should provide less sibling parallelism than broad without
collapsing all work into one directory.

Reserved flat layout

The legacy broad topology demonstrates an independently useful extreme: one directory with a very
large entry population. A future flat layout may make that workload explicit and versioned. This
design reserves the concept but does not create data, expose a selectable empty series, or reinterpret
legacy broad measurements as flat.

Preparation and collection lifecycle

For each commit, a local collection run performs the following lifecycle:

  1. Determine the complete layout recipes and maximum count before measuring anything.
  2. Materialize both prepared layouts in the authorized memory-backed fixture location.
  3. Validate every anchor's exact population, containment, topology limits, and canonical hash.
  4. Record the immutable layout identities and anchor hashes in the report plan.
  5. Measure all worker counts and file counts for the first layout, then repeat for the second.
  6. Verify that fixture metadata and hashes are unchanged before releasing the layouts.

The required iteration order is:

commit -> layout -> worker count -> file count -> task/tool/sample

The collector may still interleave participants and samples according to the existing bias-control
policy within a cell. Warm-up and measured runs reuse the same anchor. The design does not attempt to
produce cold-cache filesystem results: local memory-backed fixtures, stable topology, and comparable
fragmentation history are the intended contract.

Both layouts remain available for the whole local commit run. This permits deterministic reuse and
avoids rematerialization effects between worker counts. If CI later adopts the layouts and cannot
hold both at once, it may prepare, measure, verify, and release one complete layout before preparing
the next. That difference must be recorded in the environment contract if it can affect
compatibility.

Interruption must not publish a partial dataset as complete. Completed cells remain retryable, and a
retry must validate or rebuild the prepared layout before reusing them. No resume path may infer a
layout revision solely from a directory name.

Dataset identity and report schema

The dataset recipe gains an ordered layouts structure. Each entry contains at least:

Field Purpose
name Stable logical family (broad, deep, or a future flat)
revision Immutable topology revision
fixture_revision Generator and manifest semantics
counts Supported exact regular-file counts
anchor_policy Containment order and anchor naming rule
topology Depth, fanout, per-directory population, and remainder rules
special_entries .gitignore and symlink placement/counting rules
generator_identity Code or declarative recipe identity needed for deterministic rebuilds

Reports store the layout name and revision on every fixture and result cell, plus the concrete
anchor hash. Dataset identity includes the complete registered layout definitions, not merely their
display names. A report lacking structured layout identity is interpreted as its explicit legacy
fixture contract; it is never silently upgraded.

Compatibility and baseline selection require equal layout revision, fixture revision, anchor count,
tree hash semantics, and relevant topology parameters. Aggregation, normalization, chart lines, and
performance alarms must not cross a layout-revision boundary. If CI later switches, the viewer shows
a visible compatibility cutoff unless old revisions are deliberately remeasured with the new layout.

Sharding and retry keys currently organized around file count, workers, and shape must add layout
revision and anchor identity. Two layout revisions with the same logical name are distinct work and
cannot satisfy one another's completion records.

Viewer and command presentation

The dataset list, selected-dataset metadata, aggregated history, and full measurement list show the
versioned layout names used by the selected dataset. Detailed task/cell views show the concrete
layout revision and anchor count. This makes it possible to understand a historical row without
consulting its raw JSON.

The viewer is driven by report layout metadata. It must not hardcode that the only shapes are
broad and deep, and it must not expose reserved layouts for which the selected dataset has no
measurements. Legacy series remain labeled with their legacy revision. A layout change is rendered
as a boundary or separate series, never as an unexplained continuation.

Retiring obsolete four-worker datasets

The hosted one/four-worker datasets are obsolete now that the supported hosted grid is one/three.
Their retirement is independent of whether CI ever adopts the revised layouts.

Before removal, audit each dataset's retained reports and provenance references. If no published
artifact, baseline, or reproducibility record requires them, remove the underlying retained reports
through the publication/storage workflow. Because the dataset catalog is generated, deleting a
catalog row alone is not a durable operation. If provenance must remain, mark the dataset retired and
exclude it from the active dataset list while preserving immutable raw reports and direct historical
access. Retirement must not delete the active one/three-worker datasets.

Local experiment and acceptance gate

Remeasure the same selected revision range on the two participating local machines using both revised
layouts. Use one frozen driver/layout implementation and the same reference-tool identities for each
machine. The experiment records preparation time and peak fixture storage separately from timed
search results.

The comparison report evaluates:

  • exactness, determinism, and variance across repetitions;
  • total collection runtime and peak storage;
  • sensitivity to increasing file counts;
  • one-worker versus multi-worker scaling;
  • whether broad exposes useful directory parallelism;
  • whether deep remains a meaningful constrained-topology workload;
  • representativeness of the directory populations; and
  • clarity of layout changes in the viewer.

Only after reviewing those results is a CI choice made. The documented choices are:

  1. retain legacy CI layouts for historical continuity;
  2. switch at an explicit revision cutoff;
  3. collect legacy and revised layouts temporarily to establish overlap; or
  4. adopt only one revised layout where cost or signal justifies it.

A CI switch requires a storage/runtime estimate for hosted Linux and macOS, successful publication
of a trial dataset, and an explicit decision about whether selective historical backfill is worth its
cost. There is no presumption that local adoption implies CI adoption.

Implementation sequence

  1. Implemented - registry and schema: introduce declarative layout definitions and structured versioned layout
    identity while preserving legacy-report decoding.
  2. Implemented - generator prototype: choose and document concrete broad/deep topology parameters; generate
    the maximum trees and prove exact anchor containment.
  3. Implemented - prepared-layout API: separate materialization and validation from timing, and provide anchors
    as immutable traversal roots.
  4. Implemented - collector lifecycle: change generated local collection to commit/layout/worker/count order,
    retain both layouts, and verify post-run hashes.
  5. Implemented for local reports - report, retry, and shards: include layout revision and anchor identity in cell keys, completion
    state, merge validation, and retry behavior.
  6. Implemented - catalog and viewer: derive layout labels and available choices from report metadata, render
    revision boundaries, and prevent incompatible aggregation.
  7. Local pilot: run both machines, publish or inspect the isolated experimental datasets, and
    write the evidence-based CI recommendation.
  8. Dataset retirement: audit and retire/remove obsolete one/four-worker hosted datasets without
    disturbing retained provenance.
  9. CI decision: retain, overlap, partially adopt, or cut over according to the acceptance gate.

Steps 1-6 must land together if partial schema support could publish ambiguous data. The local pilot
may use an explicitly experimental, non-default dataset family until its reports pass normal catalog
validation.

Required validation

Unit and integration coverage must establish:

  • exact regular-file counts at every anchor and correct nested containment;
  • deterministic topology, content, canonical hashes, and identity;
  • registered broad depth/fanout bounds and registered deep depth/fanout bounds;
  • unchanged layout hashes before and after all measurements;
  • rejection of an unknown layout revision or a report whose recipe and cells disagree;
  • no compatibility, aggregation, alarms, or chart segments across revisions;
  • retry and shard merging distinguish revisions and preserve completed valid cells;
  • legacy reports retain their old identity and remain viewable;
  • catalog and all viewer modes display the selected dataset's layout revisions;
  • an unavailable reserved layout is absent from controls;
  • interrupted preparation/measurement cannot publish a complete dataset; and
  • obsolete dataset retirement preserves all data selected by the retention audit.

The end-to-end test should prepare the smallest practical registered scale set, measure more than one
worker count, resume after a simulated interruption, merge shards, generate the catalog, and render
both compact and detailed history.

Risks and open parameters

  • The registered broad fanout, files-per-directory target, deep group size, and maximum depth are now
    frozen for revision 2. Changing any of them creates another layout revision.
  • Anchor nesting adds directories to every larger traversal. The topology must be judged as a whole;
    anchors cannot be dismissed as unmeasured scaffolding.
  • Reusing one physical tree stabilizes inode and fragmentation history within a run, but host-level
    allocation can still differ between machines and rematerializations.
  • Worker-first iteration can introduce thermal or temporal bias across file counts. Existing sample
    interleaving remains in force, and the local pilot must inspect ordering effects before CI adoption.
  • Keeping both maximum layouts resident may exceed hosted capacity. This is why the initial rollout is
    local and why sequential per-layout CI preparation remains an allowed later implementation.
  • Fixture mutation by a benchmarked tool would invalidate all later anchors. Pre/post validation is
    mandatory even though the current task set is intended to be read-only.

Non-goals

This work does not change sampling counts, reference-tool semantics, correctness oracles, warm/cold
cache policy, or the meaning of custom imported fixtures. It does not switch CI layouts now, collect
the reserved flat layout, relabel old data, pool incompatible histories, or require historical
backfill before the local experiment can begin.
